# 화면 및 데이터 설계안

2026-11-02 구현 메모: 저장소 루트에 HTML·CSS·JS 기반 4페이지 데모와 공통 탐색을 추가했다. 실제 지도·크롤링·인증·DB는 연결하지 않았다. 현재 동작과 담당 파일은 [README](../README.md), 서버 연결 계약은 [API 초안](api.md), 저장소 선택은 [DB 설계안](database.md)을 따른다. 아래는 기존 설계와 검토 사항이며 모두 구현 완료를 뜻하지 않는다.

기존 설계 기준: 2026-10-17. 3페이지는 2026-10-28 사용자 결정으로 갱신했다. ‘확정’은 기존 합의 또는 명시된 사용자 결정, ‘제안’은 구현 전 검토할 설계이다.

## 화면 1 — 지도·메뉴 / 강민재

확정된 데스크톱 배치:

```text
공통 사이드바: 페이지 이동 / 메뉴 검색은 2페이지
┌──────────────────────┬─────────────────────────┐
│ 지도                 │ 선택 카페의 메뉴 정보    │
│ 현재 위치 요청       │ 이름·가격·당류·칼로리    │
│ 기본 위치: 숭실대    │ 가장 작은 사이즈 기준   │
│ 대상 카페 선택       │ [상세 보기]             │
└──────────────────────┴─────────────────────────┘
```

흐름: 접속 → 위치 요청 → 허용 시 현재 위치 / 미제공 시 숭실대 → 카페 선택 → 메뉴 확인 → 상세 보기.

길 안내는 추후 추가한다. ‘비교에 추가’는 2페이지에 배치하는 방향이다. 위 배치는 설계이며 실행 화면이 아니다.

## 화면 2 — 카테고리 검색 / 강다은

확정: 카테고리 선택 + 브랜드 선택 → 결과 목록 → 메뉴 상세 → 로그인 사용자 즐겨찾기.

배치 예정: 검색 결과에서 ‘비교에 추가’. 추가 후 표시·저장 방식은 미정이다.

카테고리는 카페인, 디카페인, 요거트, 아이스크림&빙수, 라떼, 프라페&스무디, 과일이다. ‘카페인’과 ‘라떼’처럼 분류가 겹칠 수 있으므로 단일 분류·복수 태그 여부를 결정해야 한다. 임의로 메뉴를 분류하지 않는다.

제안: 상단에 카테고리와 브랜드 필터를 두고 하단에 결과 목록을 둔다. 선택 개수, 정렬 방식, 모바일 배치는 추가 협의한다. 별도 장바구니·비교 화면은 시간 여유 시 구현한다.

## 화면 3 — 트렌드·신메뉴 / 현준혁

2026-10-28 사용자 결정: 최근 논의한 트렌드·신메뉴 정보를 모아 보여주는 페이지로 변경한다. **기존 랜덤 추천은 제외한다.**

구성 방향:

- 최신 음료 트렌드 정보 모음.
- 브랜드별 신메뉴·시즌 메뉴 정보 모음.
- 관련 메뉴의 가격·당류·칼로리 확인 및 공통 메뉴 상세 연결.

제안: 트렌드와 신메뉴를 구분한 영역을 두고 출처·집계 기간 또는 확인 시각을 표시한다. 구체적인 배치·필터·정렬 기준은 미정이다.

수집·연동 검토안: 브랜드별 수집기로 공식 사이트의 HTML 또는 JSON을 읽고, 공통 형식으로 검증·저장한 데이터를 조회한다. 사이트별 선택자·필드를 확인하며, 같은 구조의 상세 페이지는 주소를 바꿔 반복 처리한다. 수집 기술과 자동 갱신 주기는 확정하지 않았다.

유행 판단: 공식 메뉴 수집만으로 인기를 확정하지 않는다. 검색 관심도 등 별도 근거의 도입 여부와 판단 기준은 추가 결정한다. 최초 발견일은 실제 출시일과 구분하고, 첫 수집에서 발견한 모든 메뉴를 신메뉴로 표시하지 않는다. 수집 실패 시 기존 데이터를 유지하는 처리를 검토한다.

## 화면 4 — 로그인·마이페이지 / 한정원

확정: 로그인 화면, 즐겨찾기한 음료 목록, 위치 등 권한 확인.

제안: 비로그인 상태에서는 로그인 폼, 로그인 후에는 즐겨찾기 목록과 권한 상태를 표시한다. 권한 변경은 브라우저·기기 설정 안내를 통해 처리하는 흐름을 검토한다. 로그인 수단, 회원가입 여부, 계정 저장·세션 방식은 추가 결정한다.

## 공통 메뉴 상세

확정: 메뉴 이름, 브랜드, 가격, 당류, 칼로리, 최소 사이즈를 표시한다.

비교 기준: **각 메뉴의 가장 작은 사이즈 · 기본 레시피 · 옵션 추가 및 변경 없음.**

제안: 데이터 출처·확인일·제공 용량·온도 구분도 관리한다. 당류는 g, 열량은 kcal, 가격은 원 단위를 명시하고, 공식 자료의 1회 제공량 기준을 확인한다. 보고서 화면에는 [스타벅스 실제 메뉴 3종의 예시](menu-example.md)를 반영했다. 전체 브랜드·메뉴의 데이터 수집은 아직 완료하지 않았다.

## 데이터 구조 제안

| 객체 | 주요 필드 | 목적 |
| --- | --- | --- |
| Brand | id, name | 4개 브랜드 식별 |
| Store | id, brandId, name, latitude, longitude | 지도 매장 표시 |
| Menu | id, brandId, name, categoryTags | 지도·검색·트렌드 페이지 공통 메뉴 |
| MenuServing | menuId, sizeLabel, volumeMl, temperature, priceKrw, sugarG, caloriesKcal, sourceUrl, checkedAt | 최소 사이즈·제공량별 정보 보존 |
| User | id, authenticationReference | 로그인 사용자 식별 |
| Favorite | userId, menuId | 사용자별 즐겨찾기 |

제안 규칙: Favorite의 userId + menuId 중복을 제한한다. 메뉴·사이즈·온도별 공식 제공량을 구분하고, 최소 사이즈 결정 규칙을 먼저 정한다. 누락 값은 null로 보관한다. 실제 DB·API·인증 기술은 미정이다.

## 모듈 간 연결 제안

공통 메뉴 데이터 → 지도 메뉴 목록 / 카테고리 결과 / 트렌드·신메뉴 관련 메뉴.

공식 사이트 수집 → 메뉴·신메뉴 데이터 검증·저장 → 3페이지 표시. 외부 트렌드 근거와 메뉴의 연결 방식은 추가 설계한다.

로그인 사용자 식별 → 즐겨찾기 추가·조회. 위치·권한 상태 → 지도 시작점 / 마이페이지 권한 표시.

각 담당자는 공통 메뉴 ID, 카테고리, 단위, 로그인 상태 전달 형식을 먼저 맞춘다. HTML·CSS·JavaScript를 사용하는 기본 구현안을 검토하되, 프레임워크·지도 SDK·백엔드는 확정하지 않는다.
